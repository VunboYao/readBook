# 06 · 性能与并发特性

**一句话目标**：理解重渲染原因；会用 `memo` / `startTransition` / `useDeferredValue`；知道 Profiler 与 React Compiler 的定位。

## Vue ↔ React 对照

| Vue | React |
|-----|-------|
| 依赖收集 → 小组件更新 | 默认父渲染子也渲染（除非 memo/拆分） |
| `v-once` / `v-memo` | `React.memo` / Compiler |
| 计算属性缓存 | `useMemo` |
| — | `startTransition` / `useDeferredValue` |
| 虚拟列表（自研/库） | 同左（react-window 等） |

## 谁在重渲染？

触发源：

1. 自身 `setState` / `useReducer`
2. 父组件重渲染（默认传新 props）
3. 消费的 Context value 变了
4. 强制刷新（极少）

```tsx
import { memo, useState, useCallback } from 'react'

const Row = memo(function Row({
  item,
  onSelect,
}: {
  item: Item
  onSelect: (id: string) => void
}) {
  return <li onClick={() => onSelect(item.id)}>{item.title}</li>
})

function List({ items }: { items: Item[] }) {
  const [selected, setSelected] = useState<string | null>(null)
  const onSelect = useCallback((id: string) => setSelected(id), [])
  return (
    <ul>
      {items.map((item) => (
        <Row key={item.id} item={item} onSelect={onSelect} />
      ))}
    </ul>
  )
}
```

- `memo` 浅比较 props；回调不稳定 → memo 失效 → 配 `useCallback`。

## 并发：transition 与 deferred

```tsx
import { useState, startTransition, useDeferredValue, useMemo } from 'react'

function Search({ all }: { all: string[] }) {
  const [text, setText] = useState('')
  const deferred = useDeferredValue(text)
  const result = useMemo(
    () => all.filter((x) => x.includes(deferred)),
    [all, deferred],
  )

  return (
    <>
      <input
        value={text}
        onChange={(e) => {
          const v = e.target.value
          setText(v) // 紧急：输入要跟手
          // 或：startTransition(() => setQuery(v)) 让过滤降为过渡更新
        }}
      />
      <ul>
        {result.map((x) => (
          <li key={x}>{x}</li>
        ))}
      </ul>
    </>
  )
}
```

| API | 作用 |
|-----|------|
| `startTransition` | 标记更新为可中断、低优先级，保输入流畅 |
| `useDeferredValue` | 推迟基于某值的昂贵衍生渲染 |
| `useTransition` | 同上，并给 `isPending` |

## React Compiler

- 编译期自动插入等价 memo，减少手写 `useMemo`/`useCallback`/`memo`。
- 工作上：遵循 Hooks 规则与纯渲染；不要「为了 Compiler」写歪代码。
- 未开 Compiler 的老项目：该 memo 再 memo，别全项目包一层。

## 长列表

- 虚拟列表（只渲染视口）
- 分页 / 无限滚动 + Query
- 稳定 `key`；大行组件拆分

## Profiler

- React DevTools Profiler：看哪次提交、哪棵子树耗时。
- 先量再优化；忌过早 `memo` 全家桶。

## 工作约定

- 性能问题先查：**状态是否放太高**、**Context 是否过粗**、**列表是否该虚拟化**。
- 输入框跟手；重计算进 transition/deferred。
- 打开 DevTools 的「高亮更新」辅助排查。

## 踩坑

1. 无脑 `memo` 每个组件 → 比较成本 + 代码噪音。
2. `useMemo` 依赖错误 → 缓存脏数据。
3. 在列表 item 里写内联 `onClick={() => ...}` 又包 memo → 白包。
4. 用 index key + 本地 state → 「性能」与「正确性」双杀。

## 面试点 / 工作经验点

### Q1：什么时候不该用 memo？
**标签**：`面试` `工作经验`

**A**：props 每次都变、子树很轻、或 Compiler 已覆盖。memo 有比较成本。优先理清状态边界。

### Q2：`startTransition` 解决什么问题？
**标签**：`面试` `原理`

**A**：把「非紧急 UI 更新」降优先级，让紧急更新（输入）先提交，避免大列表过滤卡住打字。对应 Concurrent 能力，底层与 Fiber 可中断渲染相关。

### Q3：长列表你怎么做？
**标签**：`面试` `工作经验`

**A**：虚拟列表 + 稳定 key + 行组件轻量化；数据层分页；避免整表进 Context。能说清「只渲染可视区」即可。

### Q4：Profiler 你怎么用？
**标签**：`工作经验`

**A**：复现卡顿 → 录制 → 看 Ranked/Flamegraph → 定位提交里最贵组件 → 再决定拆状态或 memo。没有数据不空谈优化。

### Q5：React Compiler 能替你省什么？
**标签**：`面试` `工作经验`

**A**：省大量手工 memo 样板，减少因漏 memo 导致的多余渲染。不能替代错误的数据流设计，也不能替代虚拟列表。

### Q6：父组件渲染一定导致子组件渲染吗？
**标签**：`面试` `原理`

**A**：函数组件默认会跟着重跑；`memo` 且 props 浅相等可跳过；Context 消费者只在 value 变时；外部 store + selector（Zustand）可精细订阅。

### Q7：Fiber 调度和性能的关系怎么讲？
**标签**：`面试` `原理`

**A**：更新被拆成可中断单元，高优先级（用户输入）可插队。`startTransition` 显式把更新标成过渡优先级。面试点到「可中断 + 优先级」即可。

### Q8：常见性能反模式有哪些？
**标签**：`工作经验`

**A**：巨型 Context；在 render 里创建大数组/随机 key；列表不虚拟化；在 Effect 里 setState 连环触发；把服务器列表深拷贝进多个 store。
