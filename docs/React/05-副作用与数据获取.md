# 05 · 副作用与数据获取

**一句话目标**：正确使用 Effect；理解「列表请求默认不该塞 Effect」；用 TanStack Query 处理服务端状态与竞态。

**怎么读**：日常写代码看正文；想通「为何比 Vue 难 / 官方五章在补什么」看「详解」。练习场：`React/playground` → `#05`。

---

## Vue ↔ React 对照

| Vue | React |
|-----|-------|
| `onMounted` 里 axios | 常被写成 `useEffect`+fetch（可跑，但不最优） |
| Pinia 存接口数据 | 更推荐 TanStack Query 管服务端缓存 |
| `watch(id, fetch)` | `useQuery({ queryKey: ['x', id] })` |
| 取消请求 | `AbortController` / Query 自动取消 |
| — | Effect = 同步**外部系统**，不是数据层默认入口 |

## Effect 正确职责

```tsx
useEffect(() => {
  const controller = new AbortController()
  // 订阅、命令式 DOM、与非 React 控件同步
  const ro = new ResizeObserver(() => {})
  ro.observe(el)
  return () => {
    controller.abort()
    ro.disconnect()
  }
}, [el])
```

官方倾向：

- **事件响应里改状态**（点击、提交）→ 事件处理器
- **需要显示的数据** → 路由 loader / Query / RSC
- **与外部系统同步** → Effect

## 反模式：把请求塞进 Effect（仍常见）

```tsx
// 能跑，但要自己处理：loading / error / 竞态 / 缓存 / 重复请求
useEffect(() => {
  let cancelled = false
  setLoading(true)
  fetch(`/api/users/${id}`)
    .then((r) => r.json())
    .then((data) => {
      if (!cancelled) setUser(data)
    })
    .finally(() => {
      if (!cancelled) setLoading(false)
    })
  return () => {
    cancelled = true
  }
}, [id])
```

`id` 快速切换时，必须防**竞态**（旧请求后返回覆盖新数据）。

## TanStack Query 工作流

```tsx
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query'

function User({ id }: { id: string }) {
  const { data, isPending, isError, error } = useQuery({
    queryKey: ['user', id],
    queryFn: async ({ signal }) => {
      const res = await fetch(`/api/users/${id}`, { signal })
      if (!res.ok) throw new Error('fail')
      return res.json() as Promise<User>
    },
  })

  if (isPending) return <p>loading</p>
  if (isError) return <p>{error.message}</p>
  return <div>{data.name}</div>
}

function UpdateUser() {
  const qc = useQueryClient()
  const mutation = useMutation({
    mutationFn: (body: Partial<User>) =>
      fetch('/api/users', { method: 'PATCH', body: JSON.stringify(body) }),
    onSuccess: () => qc.invalidateQueries({ queryKey: ['user'] }),
  })
  return (
    <button type="button" onClick={() => mutation.mutate({ name: 'Neo' })}>
      更新
    </button>
  )
}
```

| 概念 | 含义 |
|------|------|
| `queryKey` | 缓存主键；参数必须在 key 里 |
| `staleTime` | 多久内算新鲜，不自动 refetch |
| `invalidateQueries` | 写后让读失效 |
| `signal` | 自动接入取消 |

Provider 挂在应用根：`QueryClientProvider`。

## 详解：为何 Effect 比 Vue 难 + 官方五章对照

> playground `#05` 故意偏「上班怎么选」；官方五章偏「如何想清楚」。二者不矛盾。

### 根因：Vue 藏了依赖收集，React 摊开副作用协议

| | Vue | React |
|--|-----|-------|
| 渲染 | Proxy 精确更新 | 状态变 → 组件函数整段重跑 |
| 「何时重跑副作用」 | `watch` / `watchEffect` 自动追依赖 | **你必须写 deps**，框架不追踪 Effect 体内读了谁 |
| 派生值 | `computed` | **渲染时直接算**，多数不需要副作用 |
| 用户动作 | 事件里改 `ref` | 事件里 `setState`，**不要绕 Effect** |

一句话：**不是 Effect API 难，是 React 把「渲染」和「同步外部世界」拆开了，再叠加早期滥用，官方只能用五章纠偏。**

写代码只问三句：

1. **是不是在同步外部世界？**（订阅、定时器、非 React 控件、`document.title`）→ Effect  
2. **是不是用户点了 / 提交了才发生？** → 事件处理器，不是 Effect  
3. **是不是服务器有源真相的数据？** → Query / loader / RSC，不是手写 Effect 当数据层  

### 官方五章 ↔ Vue ↔ 最小结论

| 官方章节 | 在补什么 | Vue 近似 | 工作结论 |
|----------|----------|----------|----------|
| 1. 用 Effect 同步 | Effect = 对齐外部系统 | `onMounted` 订订阅 + `onUnmounted` 清理；或 `watch` 对接第三方 | 定时器 / WebSocket / video DOM API → Effect |
| 2. 可能不需要 Effect | 派生、事件改状态不该副作用 | `computed`；事件里直接改状态 | `fullName`、filter 列表 → 渲染时算 |
| 3. 响应式 Effect 生命周期 | deps 变 → cleanup → 再 setup | `watch` 重跑 / `watchEffect` 的 stop | 依赖变了等于「拆掉旧同步、建新同步」 |
| 4. 将事件从 Effect 分开 | 「响应用户」≠「跟 props/state 同步」 | 事件处理 vs `watch`，边界本来就清 | 发消息、打点、提交 → `onClick`；别 `watch(draft)` |
| 5. 移除 Effect 依赖 | 闭包陈旧、无意义重订、deps 地狱 | 依赖自动收集，少踩 | 能下沉状态、拆对象、事件读最新就别硬塞 deps |

### 1. 使用 Effect 进行同步

```tsx
// ✅ 外部系统：浏览器时钟
useEffect(() => {
  const id = setInterval(() => setNow(new Date().toLocaleTimeString()), 1000)
  return () => clearInterval(id)
}, [])
```

```vue
<!-- Vue 近似 -->
<script setup>
import { onMounted, onUnmounted, ref } from 'vue'
const now = ref('')
let id
onMounted(() => {
  id = setInterval(() => { now.value = new Date().toLocaleTimeString() }, 1000)
})
onUnmounted(() => clearInterval(id))
</script>
```

### 2. 可能不需要 Effect（高频误用）

```tsx
// ❌ 用 Effect「同步」派生状态 —— 多一次渲染，且易不同步
const [first, setFirst] = useState('Ada')
const [last, setLast] = useState('Lovelace')
const [fullName, setFullName] = useState('')
useEffect(() => {
  setFullName(`${first} ${last}`)
}, [first, last])

// ✅ 渲染时直接算（≈ Vue computed）
const fullName = `${first} ${last}`
```

同理：列表 filter、把 props 抄进 state「备用」——多数不该 Effect。

### 3. 响应式 Effect 的生命周期

```text
渲染 (roomId=A) → commit → Effect setup（连接 A）
     ↓ roomId 变 B
渲染 (roomId=B) → commit → cleanup（断 A）→ setup（连 B）
     ↓ 卸载
                      → cleanup（断 B）
```

对应 Vue：`watch(roomId, connect, { flush... })` 换 id 会停旧逻辑再跑新逻辑。  
React 只是要求你：**cleanup 必须写对**；Strict Mode 开发态会故意 mount→cleanup→mount，暴露漏清理。

### 4. 将事件从 Effect 分开

```tsx
// ❌ 草稿一变就「发送」——把事件当成了同步
useEffect(() => {
  if (draft) sendMessage(draft)
}, [draft])

// ✅ 用户点发送才发生 —— 事件
function onSend() {
  sendMessage(draft)
  setDraft('')
}
```

```tsx
// ✅ Effect：跟 props 同步外部播放器（非 React 控件）
useEffect(() => {
  if (isPlaying) videoRef.current?.play()
  else videoRef.current?.pause()
}, [isPlaying])

// ✅ 事件：用户点按钮 —— 只改 React state
<button type="button" onClick={() => setIsPlaying((p) => !p)}>
  {isPlaying ? 'Pause' : 'Play'}
</button>
```

边界：`isPlaying` → video DOM 是**同步外部系统**（要 Effect）；点击切换 `isPlaying` 是**事件**。

### 5. 移除 Effect 依赖（降复杂度，不是删 lint）

常见策略：

| 手段 | 何时 |
|------|------|
| 函数式更新 `setX(x => …)` | 下一状态只依赖上一状态，不必把 `x` 放进 deps |
| 渲染时算派生 | 去掉「同步 state→state」的 Effect |
| 事件里读最新 | 动作不该在 Effect 里 |
| `useRef` 存最新回调 / 值 | 要订长期订阅，又不想因回调引用变而重订 |
| 拆小对象 / 下沉状态 | 避免 deps 里放每次新建的对象字面量 |

目标不是「deps 越少越好」，而是**依赖真实反映「这份同步依赖哪些输入」**。

### 和 Vue 对照：复杂度被挪到哪？

| 场景 | Vue | React（正确姿势） |
|------|-----|-------------------|
| `fullName = first + last` | `computed` | 渲染时直接算 |
| 点击后改本地状态 | 事件里改 `ref` | 事件里 `setState` |
| `id` 变了重新拉用户 | `watch` / `useAsyncData` | `useQuery({ queryKey: ['user', id] })` |
| 订 WebSocket / 改 title | `onMounted` + cleanup | `useEffect` + cleanup |
| Effect 既要最新值又不要重订 | 少踩 | 事件拆分 / ref /（进阶）Effect Event |

2. 口头用「三问」过一遍自己项目里的 `useEffect`。

## 工作约定

- SPA 服务端状态：**Query 为主**；客户端 UI 状态：`useState` / Zustand。
- `queryKey` 约定：`['domain', ...params]`，团队统一。
- Strict Mode 开发态 Effect 双调用：清理函数必须幂等；不要用「只跑一次」赌业务正确性。
- 全局 loading 用 Query 的 `isFetching` 或布局级 Suspense，避免满屏布尔地狱。

## 踩坑

1. Effect 依赖里放对象/函数字面量 → 每次新引用 → 死循环。
2. 忘记 cleanup → 泄漏与 setState on unmounted 警告。
3. 把 Query 数据再抄一份进 Zustand → 双源真相。
4. `staleTime: 0` 导致切页狂刷；按业务调。
5. 用 Effect 把 props 同步进 state「备用」→ 双份状态，易不同步（多数应直接用 props 或渲染时派生）。

## 面试点 / 工作经验点

### Q1：为什么说「请求不该默认写在 useEffect」？
**标签**：`面试` `工作经验`

**A**：Effect 表达的是同步外部系统。数据获取还需要缓存、去重、重试、失效、SSR 对齐；用 Effect 手写这些易漏竞态。路由 loader / Query / RSC 更合适。存量项目大量 Effect 请求能跑，但新代码优先 Query。

### Q2：请求竞态是什么？怎么解？
**标签**：`面试` `原理`

**A**：先发后至：旧请求晚到覆盖新 UI。解法：`AbortController`、忽略过期标志、`queryKey` 切换时 Query 自动取消。面试要能画时间线。

### Q3：如何设计 queryKey？
**标签**：`工作经验` `面试`

**A**：包含影响结果的全部参数（id、筛选、分页）。同 key 共享缓存；改参换 key。不要把非序列化对象随便塞进 key。

### Q4：缓存失效策略怎么说？
**标签**：`工作经验`

**A**：突变成功后 `invalidate` 相关 key，或 `setQueryData` 精确改缓存。乐观更新配合 `onError` 回滚。按页面设 `staleTime`/`gcTime`。

### Q5：Strict Mode 为什么 Effect 跑两次？
**标签**：`面试` `原理`

**A**：开发环境故意 mount→cleanup→mount，暴露漏清理的订阅。生产不会双调。正确做法是写好 cleanup，而不是删 Strict Mode。

### Q6：客户端状态 vs 服务端状态？
**标签**：`面试` `工作经验`

**A**：服务端状态：有源真相在后端、需缓存与过期（用户资料、列表）。客户端状态：仅 UI（弹窗开闭、向导步数）。混为一谈是中级常见问题。

### Q7：AbortController 和 cancelled 标志怎么选？
**标签**：`工作经验`

**A**：能 abort 就 abort（省带宽）；仅防 setState 时 cancelled 标志也行。Query 已封装则交给库。

### Q8：和 Vue `onMounted` + Pinia 请求对比怎么讲？
**标签**：`面试`

**A**：Vue 里也常在生命周期请求；Pinia 适合客户端全局。React 社区把「服务端缓存」独立成 Query，和 Pinia/Zustand 分工更清晰。Nuxt 的 `useFetch`/`useAsyncData` 更接近 Query + SSR。

### Q9：为什么 React Effect 比 Vue watch 难讲清楚？
**标签**：`面试` `原理`

**A**：Vue 有依赖收集，watch 自动知道盯谁；React 渲染是纯函数重跑，Effect 依赖需显式声明，且要和「事件」「派生计算」划界。官方五章主要在纠「把 Effect 当 onMounted/watch 万能桶」。

### Q10：举一个必须用 Effect、一个不该用 Effect 的例子？
**标签**：`面试` `工作经验`

**A**：必须：订阅 WebSocket / `setInterval` 同步时钟 / 把 `isPlaying` 同步到 `<video>` DOM。不该：拼接 `fullName`、filter 列表、点击发送消息、默认列表请求（用 Query）。
