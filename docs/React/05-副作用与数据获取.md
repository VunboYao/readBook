# 05 · 副作用与数据获取

**一句话目标**：正确使用 Effect；理解「列表请求默认不该塞 Effect」；用 TanStack Query 处理服务端状态与竞态。

## Vue ↔ React 对照

| Vue | React |
|-----|-------|
| `onMounted` 里 axios | 常被写成 `useEffect`+fetch（可跑，但不最优） |
| Pinia 存接口数据 | 更推荐 TanStack Query 管服务端缓存 |
| `watch(id, fetch)` | `useQuery({ queryKey: ['x', id] })` |
| 取消请求 | `AbortController` / Query 自动取消 |
| — | Effect = 同步**外部系统**，不是数据层默认入口 |

## Effect 正确职责

```tsx
useEffect(() => {
  const controller = new AbortController()
  // 订阅、命令式 DOM、与非 React 控件同步
  const ro = new ResizeObserver(() => {})
  ro.observe(el)
  return () => {
    controller.abort()
    ro.disconnect()
  }
}, [el])
```

官方倾向：

- **事件响应里改状态**（点击、提交）→ 事件处理器
- **需要显示的数据** → 路由 loader / Query / RSC
- **与外部系统同步** → Effect

## 反模式：把请求塞进 Effect（仍常见）

```tsx
// 能跑，但要自己处理：loading / error / 竞态 / 缓存 / 重复请求
useEffect(() => {
  let cancelled = false
  setLoading(true)
  fetch(`/api/users/${id}`)
    .then((r) => r.json())
    .then((data) => {
      if (!cancelled) setUser(data)
    })
    .finally(() => {
      if (!cancelled) setLoading(false)
    })
  return () => {
    cancelled = true
  }
}, [id])
```

`id` 快速切换时，必须防**竞态**（旧请求后返回覆盖新数据）。

## TanStack Query 工作流

```tsx
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query'

function User({ id }: { id: string }) {
  const { data, isPending, isError, error } = useQuery({
    queryKey: ['user', id],
    queryFn: async ({ signal }) => {
      const res = await fetch(`/api/users/${id}`, { signal })
      if (!res.ok) throw new Error('fail')
      return res.json() as Promise<User>
    },
  })

  if (isPending) return <p>loading</p>
  if (isError) return <p>{error.message}</p>
  return <div>{data.name}</div>
}

function UpdateUser() {
  const qc = useQueryClient()
  const mutation = useMutation({
    mutationFn: (body: Partial<User>) =>
      fetch('/api/users', { method: 'PATCH', body: JSON.stringify(body) }),
    onSuccess: () => qc.invalidateQueries({ queryKey: ['user'] }),
  })
  return (
    <button type="button" onClick={() => mutation.mutate({ name: 'Neo' })}>
      更新
    </button>
  )
}
```

| 概念 | 含义 |
|------|------|
| `queryKey` | 缓存主键；参数必须在 key 里 |
| `staleTime` | 多久内算新鲜，不自动 refetch |
| `invalidateQueries` | 写后让读失效 |
| `signal` | 自动接入取消 |

Provider 挂在应用根：`QueryClientProvider`。

## 工作约定

- SPA 服务端状态：**Query 为主**；客户端 UI 状态：`useState` / Zustand。
- `queryKey` 约定：`['domain', ...params]`，团队统一。
- Strict Mode 开发态 Effect 双调用：清理函数必须幂等；不要用「只跑一次」赌业务正确性。
- 全局 loading 用 Query 的 `isFetching` 或布局级Suspense，避免满屏布尔地狱。

## 踩坑

1. Effect 依赖里放对象/函数字面量 → 每次新引用 → 死循环。
2. 忘记 cleanup → 泄漏与 setState on unmounted 警告。
3. 把 Query 数据再抄一份进 Zustand → 双源真相。
4. `staleTime: 0` 导致切页狂刷；按业务调。

## 面试点 / 工作经验点

### Q1：为什么说「请求不该默认写在 useEffect」？
**标签**：`面试` `工作经验`

**A**：Effect 表达的是同步外部系统。数据获取还需要缓存、去重、重试、失效、SSR 对齐；用 Effect 手写这些易漏竞态。路由 loader / Query / RSC 更合适。存量项目大量 Effect 请求能跑，但新代码优先 Query。

### Q2：请求竞态是什么？怎么解？
**标签**：`面试` `原理`

**A**：先发后至：旧请求晚到覆盖新 UI。解法：`AbortController`、忽略过期标志、`queryKey` 切换时 Query 自动取消。面试要能画时间线。

### Q3：如何设计 queryKey？
**标签**：`工作经验` `面试`

**A**：包含影响结果的全部参数（id、筛选、分页）。同 key 共享缓存；改参换 key。不要把非序列化对象随便塞进 key。

### Q4：缓存失效策略怎么说？
**标签**：`工作经验`

**A**：突变成功后 `invalidate` 相关 key，或 `setQueryData` 精确改缓存。乐观更新配合 `onError` 回滚。按页面设 `staleTime`/`gcTime`。

### Q5：Strict Mode 为什么 Effect 跑两次？
**标签**：`面试` `原理`

**A**：开发环境故意 mount→cleanup→mount，暴露漏清理的订阅。生产不会双调。正确做法是写好 cleanup，而不是删 Strict Mode。

### Q6：客户端状态 vs 服务端状态？
**标签**：`面试` `工作经验`

**A**：服务端状态：有源真相在后端、需缓存与过期（用户资料、列表）。客户端状态：仅 UI（弹窗开闭、向导步数）。混为一谈是中级常见问题。

### Q7：AbortController 和 cancelled 标志怎么选？
**标签**：`工作经验`

**A**：能 abort 就 abort（省带宽）；仅防 setState 时 cancelled 标志也行。Query 已封装则交给库。

### Q8：和 Vue `onMounted` + Pinia 请求对比怎么讲？
**标签**：`面试`

**A**：Vue 里也常在生命周期请求；Pinia 适合客户端全局。React 社区把「服务端缓存」独立成 Query，和 Pinia/Zustand 分工更清晰。Nuxt 的 `useFetch`/`useAsyncData` 更接近 Query + SSR。
