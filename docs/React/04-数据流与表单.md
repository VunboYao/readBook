# 04 · 数据流与表单

**一句话目标**：掌握状态提升、Context 边界、受控表单，以及 React 19 Actions / 乐观更新在工作中的用法。

## Vue ↔ React 对照

| Vue | React |
|-----|-------|
| props + emit | props + 回调 |
| `v-model` | `value` + `onChange`（或多字段对象） |
| provide/inject | Context |
| Pinia | Zustand / RTK（见 08） |
| 表单库（VeeValidate 等） | React Hook Form（见 08） |
| — | React 19：`useActionState` / `useFormStatus` / `useOptimistic` |

## 状态提升

```tsx
function Parent() {
  const [value, setValue] = useState('')
  return (
    <>
      <SearchInput value={value} onChange={setValue} />
      <ResultList keyword={value} />
    </>
  )
}

function SearchInput({
  value,
  onChange,
}: {
  value: string
  onChange: (v: string) => void
}) {
  return <input value={value} onChange={(e) => onChange(e.target.value)} />
}
```

- 多组件共享 → 提升到最近共同父级；再往上就考虑 Context / store。

## Context 适用边界

```tsx
const AuthContext = createContext<{ user: User | null } | null>(null)

function useAuth() {
  const ctx = useContext(AuthContext)
  if (!ctx) throw new Error('useAuth must be under AuthProvider')
  return ctx
}
```

| 适合 Context | 不适合 Context |
|--------------|----------------|
| 主题、locale、当前用户 | 每次按键都变的输入 |
| 权限、feature flag | 高频列表选中态 |
| 依赖注入（少变） | 大对象无拆分 → 全民重渲染 |

## 受控表单模式

```tsx
type Form = { email: string; agree: boolean }

function Signup() {
  const [form, setForm] = useState<Form>({ email: '', agree: false })

  function patch<K extends keyof Form>(key: K, value: Form[K]) {
    setForm((f) => ({ ...f, [key]: value }))
  }

  function onSubmit(e: React.FormEvent) {
    e.preventDefault()
    // validate + api
  }

  return (
    <form onSubmit={onSubmit}>
      <input
        value={form.email}
        onChange={(e) => patch('email', e.target.value)}
      />
      <label>
        <input
          type="checkbox"
          checked={form.agree}
          onChange={(e) => patch('agree', e.target.checked)}
        />
        同意
      </label>
      <button type="submit" disabled={!form.agree}>提交</button>
    </form>
  )
}
```

- 字段多、校验复杂 → 上 React Hook Form（08），避免整表每键全量重渲染。

## React 19：Actions 与乐观更新

三个 API 职责不同，常一起用，但别混成「都是乐观更新」：

| Hook | 从哪引入 | 解决什么 |
|------|----------|----------|
| `useActionState` | `react` | Action 的**结果状态** + 自带 `isPending` |
| `useFormStatus` | `react-dom` | 子组件读取**最近祖先 form** 是否在提交 |
| `useOptimistic` | `react` | 异步未完成前，先展示**假设成功**的 UI |

```tsx
import { useActionState, useOptimistic } from 'react'
import { useFormStatus } from 'react-dom'

async function saveName(_prev: string, formData: FormData) {
  const name = String(formData.get('name') ?? '')
  await fetch('/api/name', { method: 'POST', body: name })
  return name // 成功后的「真实状态」
}

function SubmitBtn() {
  // 必须在 <form> 的子孙里；读的是祖先 form 的 pending，不是自己的 props
  const { pending } = useFormStatus()
  return <button type="submit" disabled={pending}>{pending ? '提交中' : '保存'}</button>
}

function NameForm({ current }: { current: string }) {
  // name = 上一次 Action 返回值（真实源）；formAction 可直接塞给 <form action>
  const [name, formAction, isPending] = useActionState(saveName, current)
  // optimistic 默认跟 name；Transition/Action 期间可临时改显示
  const [optimistic, setOptimistic] = useOptimistic(name)

  return (
    <form
      action={async (fd) => {
        setOptimistic(String(fd.get('name') ?? '')) // 立刻改 UI
        await formAction(fd) // 等服务端；结束后 optimistic 自动回到最新 name
      }}
    >
      <p>显示：{optimistic}</p>
      <input name="name" defaultValue={name} />
      <SubmitBtn />
      {isPending && <span>…</span>}
    </form>
  )
}
```

- `useFormStatus` 必须用在**被 `<form>` 渲染的子组件**里（同组件里直接调读不到）。
- `setOptimistic` 只在 Transition / Action 上下文里有效；失败时真实 `name` 没变，UI 会回到旧值。
- Vite SPA 里 Client Actions 也能用；和 Next Server Actions 不是一回事（09）。

## 工作约定

- 默认受控；对接原生插件再非受控。
- 「谁拥有状态」写进组件注释或目录：`features/xxx` 内聚。
- Context Provider 拆文件 + 自定义 `useXxx`，禁止业务里直接 `useContext` 散落。
- 后台表单：RHF + Zod；简单搜索栏：本地 `useState` 即可。

## 踩坑

1. Context value 每次 render 新建对象 → 下游全刷；用 `useMemo` 包 value 或拆 Context。
2. 把表单状态放全局 store → 难清理、易串页。
3. 受控输入忘了 `onChange` → 输入框打不了字。
4. 乐观更新失败未回滚 → 必须有错误处理与最终一致。

## 面试点 / 工作经验点

### Q1：何时用 Context，何时用全局 store？
**标签**：`面试` `工作经验`

**A**：跨多层、变更不频繁、偏「环境/会话」→ Context。跨路由、复杂更新、要中间件/devtools/时间旅行 → Zustand/Redux。高频 UI 状态优先局部 state。

### Q2：受控 vs 非受控如何讲清楚？
**标签**：`面试`

**A**：受控：React state 是唯一真相，便于校验与联动。非受控：DOM 持有值，提交时读取。大表单用 RHF 等库，内部多用非受控注册以减渲染，对外仍好用。

### Q3：乐观更新适用什么场景？
**标签**：`工作经验` `面试`

**A**：点赞、待办勾选、改名等可预期成功的操作。先改 UI，再等服务器；失败回滚并 toast。强一致、支付类不要盲目乐观。

### Q4：Action 和传统 onSubmit 有何不同？
**标签**：`面试` `原理`

**A**：Action 把「进行中」状态（pending）一等公民化，方便 `useFormStatus` / `useActionState`。传统 `onSubmit` + 自己 `useState(loading)` 也能做；Actions 更贴合渐进增强与 React 19 表单模型。Next 里还可接到 Server Actions。

### Q5：状态提升的边界？
**标签**：`工作经验`

**A**：只提升「共享所需的最小状态」。提升过高 → prop drilling；过低 → 无法同步。中间层可用组合（children / render props）或轻量 Context。

### Q6：为什么 Context 容易引发性能问题？
**标签**：`面试` `原理`

**A**：Provider 的 `value` 引用变了，所有 `useContext` 消费者重渲染。拆分 Context、选择器库（如 `use-context-selector`）、或改用外部 store 的 selector。

### Q7：表单校验放哪一层？
**标签**：`工作经验`

**A**：字段级即时校验靠客户端；最终以服务端为准。schema（Zod）前后端共享是中大型项目常见做法。

### Q8：多步骤表单状态怎么放？
**标签**：`工作经验`

**A**：步骤内本地 state；跨步用父级 state 或轻量 store；路由 query 存 step；离开页要明确是否持久化（sessionStorage）。
