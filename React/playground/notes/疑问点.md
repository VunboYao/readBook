## `useSyncExternalStore`：订阅 React 外部 store

**日期：** 2026-08-01
**相关文件：** GlobalFeedback.tsx / loading.ts / toast.ts

**疑问：** 模块级 loading/toast（计数器 + pub/sub）如何安全驱动组件更新？`subscribe` 里的 `onStoreChange` 是什么？`getSnapshot` 返回数组会不会每次都重渲染？并发多次 `show` 会不会提前关掉？

**结论：**

`useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?)` 是 React 18 官方钩子，专门接**组件树外的可变源**（模块变量、浏览器 API、自写 store）。比 `useState` + `useEffect` 手写订阅更安全，避免并发下撕裂（tearing）。

| 参数 | 含义 |
|------|------|
| `subscribe(onStoreChange)` | 挂监听；外部变更时必须调用 React 传入的 `onStoreChange`；返回 unsubscribe |
| `getSnapshot()` | 读当前快照；React 用 `Object.is` 比较决定是否重渲染 |
| `getServerSnapshot?` | SSR/水合默认值 |

链路：`loading.show()` → `count++` → `emit()` → 调用 `onStoreChange()` → React 再 `getSnapshot()` → 重渲染 UI。`emit` 只负责通知，真正展示靠快照 + 重渲染。

`onStoreChange` 是 **React 注入的「请更新」回调**，不是业务参数；`subscribe` 里写成 `loading.subscribe(() => onStoreChange())` 是为了忽略外部 listener 的多余入参。

`getSnapshot` 必须返回**稳定引用**：同一状态下多次调用应 `Object.is` 相等。`return toasts`（变量本身）正确；`return [...toasts]` 每次新数组会疯狂重渲染。变更时再换新数组（`toasts = [...toasts, item]`）即可。

Loading 用**计数器**而非布尔：多次 `show` 时 `getSnapshot` 一直为 `true`，只有 `hide` 配平、`count === 0` 才关闭，避免并发请求被先结束的那个提前关遮罩。

类比 Vue：像模块/`Pinia` 外的非响应式源，要自己订阅；这里由该 hook 接管订阅与快照比较。

**相关代码：**

```tsx
// 外部 store：变更换引用，getSnapshot 原样返回
let toasts: ToastItem[] = []
const toast = {
  getSnapshot() {
    return toasts // 稳定；勿 return [...toasts]
  },
  subscribe(listener: (t: ToastItem[]) => void) {
    listeners.add(listener)
    return () => listeners.delete(listener)
  },
  error(message: string) {
    toasts = [...toasts, { id: Date.now(), type: 'error', message }]
    listeners.forEach((l) => l(toasts))
  },
}

// 组件：subscribe 转交 React 的 onStoreChange
function subscribeToast(onStoreChange: () => void) {
  return toast.subscribe(() => onStoreChange())
}

function GlobalFeedback() {
  const list = useSyncExternalStore(subscribeToast, toast.getSnapshot, () => [])
  return list.map((t) => <div key={t.id}>{t.message}</div>)
}
```

## `Tailwind`：常用类名规律与高频速查

**日期：** 2026-08-01
**相关文件：** airbnb-app/src/views/home/index.tsx

**疑问：** Tailwind 把基础样式拆成工具类后，类名记不清；有没有命名规律和按场景的高频速查？

**结论：**

别背几百个类，背公式：`{属性}{方向?}{-}{值}`。间距口诀：**数字 × 4 = px**（`p-4` = 16px）。颜色习惯：常态 `500`，hover `600`，浅底/浅边 `50`/`200`。装 **Tailwind CSS IntelliSense** 补全。

### 缩写对照

| 缩写 | 对应 CSS |
|------|----------|
| `p` / `m` | padding / margin |
| `w` / `h` | width / height |
| `t` `r` `b` `l` | top / right / bottom / left（顺时针） |
| `x` / `y` | 水平 / 垂直 |
| `text` | color / size / align（看后面值） |
| `bg` / `border` / `rounded` | 背景 / 边框 / 圆角 |
| `gap` | gap |

方向示例：`p-4`、`px-4`、`pt-2`、`mx-auto`。

### 尺寸阶梯（间距）

| 类 | 实际 |
|----|------|
| `1` | 4px |
| `2` | 8px |
| `3` | 12px |
| `4` | 16px |
| `6` | 24px |
| `8` | 32px |

字号另记：`text-sm` → `text-base` → `text-lg` → `text-xl` → `text-2xl`。

### Flex 口诀

- `items-*` → 交叉轴（默认横排时是竖直对齐）
- `justify-*` → 主轴（默认横排时是水平对齐）
- `gap-*` → 子元素间距

### 四句总口诀

1. **布局**：`flex` + `items`/`justify` + `gap`
2. **盒子**：`p/m` + `w/h` + `rounded` + `border/bg`
3. **文字**：`text-{size|color}` + `font-{weight}`
4. **交互**：`hover:` / `focus:` + `cursor-pointer` + `transition`

状态前缀：`hover:` `focus:` `active:` `disabled:`；断点：`sm:` `md:` `lg:`。

### 按场景组合

**按钮**

```tsx
// 实心
className="px-4 py-2 rounded-md bg-blue-500 text-white hover:bg-blue-600 cursor-pointer"

// 描边
className="px-4 py-2 rounded-md border-2 border-blue-500 text-blue-500 hover:bg-blue-50 cursor-pointer"
```

常用：`px-4 py-2`、`rounded-md`、`border-2`、`bg-blue-500`、`text-white` / `text-blue-500`、`hover:bg-blue-600`、`disabled:opacity-50`、`cursor-pointer`、`transition`。

**卡片**

```tsx
className="p-6 rounded-lg border border-gray-200 bg-white flex flex-col gap-3"
```

常用：`p-4`/`p-6`、`rounded-lg`、`border-gray-200`、`bg-white`、`shadow-md`、`overflow-hidden`、`flex flex-col gap-3`。

**表单**

```tsx
className="w-full px-3 py-2 rounded-md border border-gray-300 outline-none focus:border-blue-500 focus:ring-2 focus:ring-blue-200"
```

常用：`w-full`、`px-3 py-2`、`border-gray-300`、`outline-none`、`focus:border-blue-500`、`focus:ring-2`、`placeholder:text-gray-400`、`space-y-4`（父级）。

**页面布局**


## `EditorConfig` / `Prettier` / `ESLint`：只做缩进对齐选什么

**疑问：** 不想上完整 ESLint/Prettier，只想统一缩进对齐，用哪种合适？

**结论：**

只缩进对齐 → **EditorConfig** 就够，不必上 ESLint / Prettier。

| 方案 | 适合度 | 说明 |
|------|--------|------|
| EditorConfig | ✅ 最合适 | 只管缩进/换行/尾空格，零依赖 |

## `createRoot` / `RouterProvider`：不同路由模式下挂载根不同

**日期：** 2026-08-01
**相关文件：** airbnb-app/src/main.tsx、airbnb-app/src/router/index.tsx

**疑问：** 以前 `main.tsx` 挂 `App`；用了 `createBrowserRouter` 后直接挂 `RouterProvider`。是不是只有 Data Router 才挂 `RouterProvider`，其他模式还是挂 `App`？

**结论：**

`createRoot(...).render(...)` 挂的是整棵应用根；根上的「路由入口」随模式变，`App` 只是命名习惯，不是硬性要求。

| 模式 | `main.tsx` 通常挂什么 | `App` 角色 |
|------|----------------------|------------|
| Data Router | `RouterProvider` | 多半是布局路由（`path: '/'` 的 `Component`），不是 createRoot 的根 |
| 声明式 | `App` 或 `BrowserRouter` | 应用壳 / 写 `Routes` 的地方 |

要点：`RouterProvider` = Data Router 入口；路由表、loader、action、路由级 `lazy` 都挂在它背后的 `router` 上。外层仍可包 Redux / Theme 等 Provider。

**相关代码：**

```tsx
// Data Router：根是 RouterProvider；App 是布局路由
createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <RouterProvider router={router} />
  </StrictMode>,
)

createBrowserRouter([
  {
    path: '/',
    Component: App, // 布局：内部 <Outlet />
    children: [
      { index: true, lazy: () => import('./views/home/Home') },
    ],
  },
])

// 声明式：根常见是 App 或 BrowserRouter
function App() {
  return (
    <BrowserRouter>
      <Routes>
        <Route path="/" element={<Home />} />
      </Routes>
    </BrowserRouter>
  )
}
```

## `createBrowserRouter` / `RouterProvider`：Data Router 对象配置核心用法

**日期：** 2026-07-31
**相关文件：** 08-ecosystem.tsx、08-路由与状态生态.md

**疑问：** React Router 主流对象配置（Data Router）具体怎么用？和 JSX `<Routes>`、`useRoutes` 怎么区分？

**结论：**

新项目主流：`createBrowserRouter(routes)` + `<RouterProvider router={router} />`。history 由 router 实例自管，不再包 `<BrowserRouter>`。`router` 放模块顶层创建一次。

| 写法 | API | 说明 |
|------|-----|------|
| Data Router（主流） | `createBrowserRouter` + `RouterProvider` | 官方主推；可接 lazy / errorElement / loader |
| JSX | `BrowserRouter` + `<Routes>/<Route>` | 存量多；章节演示常用 |
| `useRoutes` | 外层 Router + `useRoutes(objects)` | 对象版 `<Routes>`，无 data APIs |

和 Vue Router 对照：`createRouter` ≈ `createBrowserRouter`；`<router-view>` ≈ `<Outlet />`；默认子路由 ≈ `index: true`；子路径用相对 `'users'` / `':id'`。

要点：

- 有 `element` 的父路由必须放 `<Outlet />`，否则子路由不渲染。
- 导航/读参 API 不变：`NavLink`、`useParams`、`useNavigate`、`useSearchParams`。
- 无 `path` 只有 `element` + `children` → pathless layout（鉴权壳常用）。
- `lazy` 返回字段是 `Component`（不是 `element`）。
- 演示隔离用 `createMemoryRouter(routes, { initialEntries })`，对象结构相同。
- 列表缓存仍用 Query；loader 多用于鉴权 `redirect` 等，不必全搬进路由。

**相关代码：**

```tsx
import {
  createBrowserRouter,
  RouterProvider,
  Outlet,
  NavLink,
  Navigate,
  useParams,
  useNavigate,
  useSearchParams,
} from 'react-router'

function RootLayout() {
  return (
    <>
      <nav>
        <NavLink to="/" end>首页</NavLink>
        <NavLink to="/users">用户</NavLink>
      </nav>
      <Outlet />
    </>
  )
}

function AuthLayout() {
  const ok = Boolean(localStorage.getItem('token'))
  if (!ok) return <Navigate to="/login" replace />
  return <Outlet />
}

function UserDetail() {
  const { id } = useParams()
  const [sp, setSp] = useSearchParams()
  const navigate = useNavigate()
  return (
    <button type="button" onClick={() => navigate(-1)}>
      返回 {id} tab={sp.get('tab')}
    </button>
  )
}

const router = createBrowserRouter([
  {
    path: '/',
    element: <RootLayout />,
    errorElement: <p>出错了</p>,
    children: [
      { index: true, element: <HomePage /> },
      { path: 'login', element: <LoginForm /> },
      {
        element: <AuthLayout />, // pathless：不增加 URL 段
        children: [
          {
            path: 'users',
            element: <UsersLayout />,
            children: [
              { index: true, element: <UserList /> },
              { path: ':id', element: <UserDetail /> },
            ],
          },
        ],
      },
      {
        path: 'heavy',
        lazy: async () => {
          const m = await import('./HeavyPage')
          return { Component: m.HeavyPage }
        },
      },
    ],
  },
])

export function App() {
  return <RouterProvider router={router} />
}
```

## `zustand`：create / set / selector 核心用法

**日期：** 2026-07-31
**相关文件：** 08-ecosystem.tsx

**疑问：** Zustand 的核心 API 怎么用？和 Pinia / Redux 怎么对照？订阅时要注意什么？

**结论：**

Zustand ≈ 轻量 Pinia：`create` 返回 hook，状态与 action 写在一起；默认无需 Provider。

| API | 作用 | 类比 |
|-----|------|------|
| `create((set, get) => …)` | 定义 store，返回 `useXxx` | `defineStore` |
| `set(partial)` / `set(s => partial)` | 浅合并更新 | `$patch` |
| `useStore(selector)` | 按 selector 精确订阅，`Object.is` 比较 | `storeToRefs` + 细粒度订阅 |
| `getState` / `setState` / `subscribe` | 组件外读写 | 任意模块直接调 |

要点：

- **永远带 selector**：`useCart((s) => s.items…)`；裸 `useCart()` 任意字段变都重渲染。
- selector 返回新对象会每次重渲染；多字段用 `useShallow`。
- 客户端 UI/会话/购物车用 Zustand；服务端缓存用 Query，别双源抄一份。

**相关代码：**

```tsx
import { create } from 'zustand'

type CartState = {
  items: { id: string; qty: number }[]
  add: (id: string) => void
  clear: () => void
}

const useCart = create<CartState>((set) => ({
  items: [],
  add: (id) =>
    set((s) => {
      const found = s.items.find((i) => i.id === id)
      if (found) {
        return {
          items: s.items.map((i) =>
            i.id === id ? { ...i, qty: i.qty + 1 } : i,
          ),
        }
      }
      return { items: [...s.items, { id, qty: 1 }] }
    }),
  clear: () => set({ items: [] }),
}))

// 只订派生值 / action
const count = useCart((s) => s.items.reduce((n, i) => n + i.qty, 0))
const add = useCart((s) => s.add)

// 组件外
useCart.getState().add('sku-1')
```

## `Effect` / `AbortSignal` / Query：接口竞态的几种处理

**日期：** 2026-07-30
**相关文件：** 05-effects-query.tsx

**疑问：** Effect 里按 `id` 请求时，快速切换会乱序返回；竞态有哪几种常见处理？`cancelled` 和 `AbortSignal` 分别是什么？

**结论：**

**竞态：** 后发的请求不一定后返回；旧响应若仍 `setState`，UI 会显示过期数据。

| 方式 | 做什么 | 网络是否停 | 典型场景 |
|------|--------|------------|----------|
| `cancelled` 标志 | cleanup 标脏，旧 `then` 里不写 UI | 否，请求照跑完 | 手写 Effect 演示 / 无法 abort 的库 |
| 序号 / generation | `reqId++`，回来时比对是否仍是最新 | 否 | 同 cancelled，显式版本号 |
| `AbortController` + `AbortSignal` | cleanup 里 `abort()`，中断进行中的工作 | 是（能响应 signal 时） | `fetch`、自管定时器/模拟请求 |
| TanStack Query 等 | `queryKey` + 内建取消/忽略过期 | 通常是（传 `signal`） | 生产推荐 |

要点：

- `cancelled: boolean`：闭包标志；**丢结果，不取消请求**。
- `AbortSignal`：Web API；由 `AbortController.signal` 得到，传给请求；`abort()` 后监听方清定时器 / 断 `fetch`，并以 `AbortError`（`DOMException`）失败。
- 生产优先 Query；手写 Effect 至少要 cancelled 或 AbortSignal，二者可并用（abort 后仍建议别对已卸载组件 setState）。

**相关代码：**

```tsx
// 1) cancelled：丢弃过期结果
useEffect(() => {
  let cancelled = false
  fetchUser(id).then((data) => {
    if (!cancelled) setUser(data)
  })
  return () => {
    cancelled = true
  }
}, [id])

// 2) AbortSignal：真正取消
function fetchUser(id: string, signal?: AbortSignal): Promise<User> {
  return new Promise((resolve, reject) => {
    const timer = window.setTimeout(() => {
      const user = DB[id]
      if (!user) reject(new Error(`user ${id} not found`))
      else resolve({ ...user })
    }, 600)
    signal?.addEventListener('abort', () => {
      window.clearTimeout(timer)
      reject(new DOMException('Aborted', 'AbortError'))
    })
  })
}

useEffect(() => {
  const ac = new AbortController()
  fetchUser(id, ac.signal)
    .then(setUser)
    .catch((e) => {
      if (e.name === 'AbortError') return
      // 处理其它错误
    })
  return () => ac.abort()
}, [id])
```

## `ref` callback：`ref` 可以是函数，参数是 DOM 节点

**日期：** 2026-07-30
**相关文件：** 05-effects-query.tsx

**疑问：** 章节里 `ref={setVideoEl}` 为什么是一个 set 函数？`ref` 支持回调时到底传了什么？

**结论：**

`ref` 除了 `useRef` 的对象，还可以是 **callback**：`(node) => void`。挂载时 React 把真实 DOM 作为 `node` 传入；卸载时传 `null`（React 19 也可 `return` cleanup）。

`setVideoEl` 签名刚好匹配，所以能直接当 callback ref：挂载 `setVideoEl(videoDOM)`，卸载 `setVideoEl(null)`。DOM 进 **state** 后可放进 Effect 依赖（`[isPlaying, videoEl]`），节点就绪会再跑一遍同步；`useRef` 改 `.current` 不触发渲染，做不到这一点。

本 demo 的 `<video>` 始终挂载时 `useRef` 也够用；`ref={setState}` 是刻意演示「同步外部系统时，DOM 本身也可以是依赖」。

| | `useRef` | `useState` + `ref={setXxx}` |
|--|----------|------------------------------|
| 节点就绪 | 不重渲染 | `setState` → 重渲染 |
| 进 Effect 依赖 | 不行 | 可以 |

文档：[ref callback API](https://react.dev/reference/react-dom/components/common#ref-callback)、[Manipulating the DOM with Refs](https://react.dev/learn/manipulating-the-dom-with-refs)

**相关代码：**

```tsx
const [isPlaying, setIsPlaying] = useState(false)
const [videoEl, setVideoEl] = useState<HTMLVideoElement | null>(null)

useEffect(() => {
  if (!videoEl) return
  if (isPlaying) void videoEl.play()
  else videoEl.pause()
}, [isPlaying, videoEl])

<video ref={setVideoEl} src="..." loop playsInline muted />
// 等价于 ref={(node) => setVideoEl(node)}
```

## `useDeferredValue`：值可以晚一点再反映到 UI


**日期：** 2026-07-29

**疑问：** `useDeferredValue` 做什么？和 `useTransition` / 防抖有什么区别？

**结论：**

把某个**已经有了的值**标成可滞后：紧急 UI（输入框）立刻用新值，重 UI（大列表）先用旧值，有空再追平。Concurrent 下可中断，**不是固定 N ms 的防抖**。

| | `useDeferredValue` | `useTransition` |
|--|--------------------|-----------------|
| 控制点 | 值已变，推迟「用新值渲染的那部分」 | 包住 `setState`，标成非紧急 |
| 典型场景 | props / 父传来的值，子组件控制不了 set | 自己触发的状态更新 |

**相关代码：**

```tsx
const [query, setQuery] = useState('')
const deferredQuery = useDeferredValue(query)
const isStale = query !== deferredQuery

<input value={query} onChange={(e) => setQuery(e.target.value)} />
<div style={{ opacity: isStale ? 0.6 : 1 }}>
  <SearchResults query={deferredQuery} />
</div>
```

## `useSelector` / `shallowEqual` / `memo`：selector 返回对象要浅比

**日期：** 2026-07-29
**相关文件：** 10-sandbox.tsx

**疑问：** `memo` 子组件里，`useSelector` 选标量时父更新不重渲，返回新对象就会重渲；是否要靠 `shallowEqual`？根因是不是不可变 + 引用？

**结论：**

归根结底是**相等怎么判**；不可变更新让「引用变了 ≈ 真变了」成立。`memo` 与 `useSelector` 是两条线：

| 谁在比 | 默认规则 | 对象陷阱 |
|--------|----------|----------|
| `memo`（props） | 浅比一层 `===` | 父每轮新对象/新函数 → 必渲 |
| `useSelector`（返回值） | 整值 `===` | selector 每次 `({ x })` 新对象 → 必渲 |

任意 action 都会让订阅的 selector **重算**；标量 `0 === 0` 跳过，新对象引用不同则 `useSelector` **自己**拉起重渲（与父是否 `memo` 跳过无关）。返回对象时加第二参 `shallowEqual`，或改选标量 / 稳定切片。

口诀：**不可变 = 用引用表达变/没变；优化 = 没变别造新引用，造了就浅比。**

**正常更新靠的是 Immer 不可变产出 + 选中值引用变化；没有对 user 内部字段做深度 diff。**

**相关代码：**

```tsx
import { useSelector, shallowEqual } from 'react-redux'
import { memo } from 'react'

// ✅ 选标量：默认 === 即可
const counter = useSelector((s: RootState) => s.counter.value)

// ❌ 每次新对象 → 无关 slice 更新也会重渲
// const { counter } = useSelector((s) => ({ counter: s.counter.value }))

// ✅ 必须返回对象时：第二参浅比
const { counter } = useSelector(
  (s: RootState) => ({ counter: s.counter.value }),
  shallowEqual
)

const Home = memo(() => <div>{counter}</div>)
```

## `useTransition`：过渡更新保交互流畅（18 特性）

**日期：** 2026-07-27

**疑问：** `useTransition` 做什么？是 React 19 新增的吗？项目里用得多吗？

**结论：**

把一部分 state 更新标成**过渡更新**（低优先级、可打断），让输入/点击等高优先级更新先响应。返回 `[isPending, startTransition]`。

**不是 19 新增**：随 React **18** 并发特性引入。19 主要是和 Actions / 表单等搭配更顺，hook 本身来自 18。

**使用频率不高**，属性能专项。对口场景：搜索框 + 大列表过滤、Tab/筛选项切重 UI、需要 `isPending` 反馈。接口慢不靠它（用 loading / Suspense）；没体感卡顿不必加。

| 紧急更新 | 过渡更新（`startTransition` 内） |
|---------|--------------------------------|
| 输入框立刻跟上 | 大列表过滤 / 重渲染可慢、可打断 |

与 `useDeferredValue`：前者包「怎么 set」；后者包「某个值晚一点再跟上」。不需要 pending 时单独用 `startTransition` 即可。

**相关代码：**

```tsx
const [isPending, startTransition] = useTransition()

function onChange(e: React.ChangeEvent<HTMLInputElement>) {
  const value = e.target.value
  setInput(value) // 紧急
  startTransition(() => {
    setFilter(value) // 过渡
  })
}
```

## `useLayoutEffect`：绘制前同步量 DOM / 防闪烁

**日期：** 2026-07-27

**疑问：** `useLayoutEffect` 和 `useEffect` 差在哪？什么时候该用？

**结论：**

API 相同，差在时机：


| | `useLayoutEffect` | `useEffect` |
|--|-------------------|-------------|
| 时机 | DOM 已更新，**绘制前** | **绘制后** |

- layout 里只做短同步活，别塞重计算/请求；SSR 常会告警，优先客户端或改 `useEffect`。

## `useImperativeHandle`：自定义 ref 暴露的命令式 API

**日期：** 2026-07-27

**疑问：** `useImperativeHandle` 是干什么的？和 Vue 的什么对应？什么时候该用？

**结论：**

用来**裁剪父组件通过 `ref` 拿到的 API**，而不是把整个 DOM / 内部状态原样暴露。对应 Vue 的 **`defineExpose`**。

| Vue | React |
|-----|--------|
| `defineExpose({ focus, clear })` | `useImperativeHandle(ref, () => ({ focus, clear }), deps)` |
| 模板 ref + `xxx.value.focus()` | `useRef` + `ref.current.focus()` |

- React 19：函数组件可直接收 `ref` prop，多数场景不必再包 `forwardRef`。
- deps 变了会重新生成暴露对象；`[]` 则对象身份稳定（闭包注意最新值）。
- **声明式优先**（props / `onXxx`）；命令式留给 focus、validate、play/pause 等少数场景。

**相关代码：**

```tsx
type InputHandle = {
  focus: () => void
  clear: () => void
}

function FancyInput({ ref }: { ref?: React.Ref<InputHandle> }) {
  const inputRef = useRef<HTMLInputElement>(null)

  useImperativeHandle(ref, () => ({
    focus: () => inputRef.current?.focus(),
    clear: () => {
      if (inputRef.current) inputRef.current.value = ''
    },
  }), [])

  return <input ref={inputRef} />
}

// 父：拿到的是自定义对象，不是 <input> DOM
const ref = useRef<InputHandle>(null)
<FancyInput ref={ref} />
<button onClick={() => ref.current?.focus()}>聚焦</button>
```

## `useCallback`：闭包陷阱与函数式更新


**日期：** 2026-07-27
**相关文件：** 10-sandbox.tsx

**疑问：** `useCallback` + `[]` 时读闭包 state 会怎样？怎样既数值正确又引用稳定？什么时候才值得用？

**结论：**

**闭包陷阱：** deps 为空却读渲染时的 state，函数永远闭着初次值。

```tsx
// ❌ 陷阱：add 引用稳定，但 total 一直按 0+1 算，界面容易卡在 1
const add = useCallback(() => {
  setTotal(total + 1)
}, [])
```

**推荐：** 函数式更新 + `[]` —— state 用 React 传入的最新值，`add` 引用不变。[]

```tsx
// ✅ 数值对，且 add 引用始终同一份
const add = useCallback(() => {
  setTotal((t) => t + 1)
}, [])
```

**陷阱 = 闭包里读了过期的 render 变量；函数式更新读的是 setter 给的当前值，两回事**

| 写法 | 数值 | `add` 引用 |
|------|------|------------|
| `setTotal(total + 1)` + `[]` | 错 | 稳定 |
| `setTotal(total + 1)` + `[total]` | 对 | 随 total 变 |
| `setTotal(t => t + 1)` + `[]` | 对 | 稳定 |

**何时值得 `useCallback`：** 传给 `memo` 子组件时才有意义；只给本组件原生 `button` 可省略。

```tsx
// 父：稳引用的 add
const add = useCallback(() => setTotal((t) => t + 1), [])

// 子：memo 后，父组件因其它 state 重渲染时，若 add 不变则这里不打 log
const Child = memo(function Child({ add }: { add: () => void }) {
  console.log('Child render')
  return <button onClick={add}>Add</button>
})

// <Child add={add} />
```

口诀：**数据在变 ≠ 函数引用在变**。

## `useCallback`：稳函数引用，而非「跟更新绑定」

**日期：** 2026-07-27

**疑问：** `useCallback` 是干什么的？是不是和更新有关、作为核心依赖时才要特殊处理？

**结论：**
- 作用：缓存函数引用；`deps` 不变时，每次 render 返回**同一个函数对象**。`useCallback(fn, deps) ≈ useMemo(() => fn, deps)`。
- **不是「一更新就要包」**，而是：**有人在意这个函数的引用变没变**时才需要。
  - 需要：传给 `memo` 子组件的 props；作为 `useEffect` / 其它 Hook / 自定义 Hook 的依赖。
  - 不需要：只在本组件 `onClick`，下游不靠引用相等。
- 口诀：不是跟「更新」绑定，而是跟「引用变化会牵动 memo / Effect 等依赖」绑定。
- 有 React Compiler 时多数可少写；没开才按上面场景手写。勿滥用（自身也有成本）。
- 对比 `useEffectEvent`：`useCallback` 仍跟 deps 走；Effect Event 是「订阅稳定、读最新值」，且主要给 Effect 用。

```tsx
// ✅ 传给 memo 子组件：稳引用才有意义
const onSave = useCallback(() => {
  save(form)
}, [form])

// ❌ 只给本组件 button：多包一层没收益
const onClick = useCallback(() => setOpen(true), [])
```

## `useEffectEvent`：订阅要稳、读取要新

**日期：** 2026-07-27
**相关文件：** 10-sandbox.tsx

**疑问：** `useEffectEvent` 解决什么？把定时器逻辑直接写进 `useEffect` 并依赖 `counter` 行不行？Effect 是否应尽量只执行一次？是不是主要为了防性能问题？

**结论：**
- **问题本质**：Effect 要「稳定订阅」（interval / WS / 原生监听），回调里又要读最新 props/state。若把回调用到的 state 全塞进 deps → cleanup 反复销毁/重建订阅；若 deps 写空/不全 → stale closure。
- **`useEffectEvent`**：抽出「事件函数」，调用时始终用最近一次渲染的值；**不要**放进 `useEffect` 依赖。Effect 只管订阅/清理。

```tsx
const onTick = useEffectEvent(() => {
  setCounter(counter + increment)
})
useEffect(() => {
  const id = setInterval(() => onTick(), 1000)
  return () => clearInterval(id)
}, []) // interval 只建一次
```

- **传统写法对比**：`useEffect` 里直接闭包 + `[counter]` 能跑，但每秒拆建定时器；更好的传统折中是 `setCounter(c => c + increment)` + `[increment]`（步长变才重建）。
- **原则不是「所有 Effect 都只跑一次」**：
  - 订阅目标变了（如换 `roomId`）→ 放进 deps，该重订阅；
  - 仅回调里读的业务 state → 用 `useEffectEvent`，别因此拆建订阅。
- **动机**：核心是正确性 + 语义拆分（「何时重订阅」≠「回调读什么」）；少重建是附带性能收益，不是设计出发点。
- **常用场景**：定时器/rAF、WebSocket、`window` 原生事件、第三方 SDK 回调、轮询心跳。普通 `onClick` 不需要。

## `useContext`：不能读到「自己提供」的值

**日期：** 2026-07-27
**相关文件：** 10-sandbox.tsx

**疑问：** `useContext` 是否必须写在父级 Provider 下？把 `useContext` 写在同一组件里（自己既 Provider 又消费）为什么读不到更新后的 theme？

**结论：**
- `useContext` 随时可调用；没有上层 Provider 时返回 `createContext(default)` 的默认值，不会报错。
 - 要共享/响应父级传入的动态值，消费方必须是 Provider 的**子组件**（或更深层后代）。
- Provider 组件自身调用 `useContext` 时，只向上找最近 Provider，**看不见自己 return 出来的那一层**；因此同组件内 `useContext` 永远是默认值（如 `'light'`），与本地 `theme` state 无关。
- 类比 Vue：`provide` 的组件里 `inject` 同一 key，拿不到自己刚 provide 的值。
- 同组件既要改又要展示：直接用本地 `theme`；跨组件再拆子组件 + `useContext`。

```tsx
const ThemeContext = createContext<'light' | 'dark'>('light')

function App() {
  const [theme, setTheme] = useState<'light' | 'dark'>('light')
  // ❌ 同组件 useContext：向上找，看不见自己 return 的 Provider → 永远是默认 'light'
  const themeFromCtx = useContext(ThemeContext)

  return (
    <ThemeContext.Provider value={theme}>
      {/* 同组件展示用本地 theme；跨组件再拆子组件读 Context */}
      <p>{theme}</p>
      <Child /> {/* ✅ Child 在 Provider 子树内，能读到 theme */}
      <button onClick={() => setTheme('dark')}>dark</button>
    </ThemeContext.Provider>
  )
}

function Child() {
  const theme = useContext(ThemeContext) // 'light' | 'dark'，跟 Provider 同步
  return <span>{theme}</span>
}
```

## `React Router`：核心知识点梳理

**日期：** 2026-07-25
**相关文件：** 10-sandbox.tsx

路由实验场的基本模型：上方导航改变 URL / 历史记录，下方 `<Routes>` 按当前 URL 匹配并渲染页面。**URL 是当前页面状态的一部分；路由表规定「什么 URL 显示什么组件」。**

### 1. 三个最核心的组件：`Routes`、`Route`、`Outlet`

```tsx
<Routes>
  <Route path="/about" element={<About />} />
</Routes>
```

- `<Routes>`：在它的子 `<Route>` 中寻找与当前地址匹配的路由，并渲染最佳匹配结果。
- `<Route path="...">`：声明匹配规则。`path` 描述 URL 形状，`element` 是匹配后渲染的 React 节点。
- `<Outlet />`：嵌套路由的「子页面占位符」。父路由先渲染自己的布局，匹配到的子路由渲染到这里。

示例地址与页面的对应关系：

| 地址 | 匹配结果 | 说明 |
|---|---|---|
| `/` | 重定向到 `/about` | 首页不直接展示内容 |
| `/about?name=querySearch&age=18` | `<About />` | 查询参数不参与 `path` 匹配，但页面可读取 |
| `/detail/1001` | `<Detail />` | `1001` 是动态路径参数 |
| `/dashboard/profile` | `<DashboardLayout><Profile /></DashboardLayout>` | 父布局中通过 `<Outlet />` 展示 `Profile` |
| 其他未定义地址 | `<Home />` | 这里的 `Home` 实际承担 404 页作用 |

### 2. 声明式导航：`Link` 与 `NavLink`

```tsx
<NavLink to="/detail/1001" state={{ id: 123, name: 'test' }}>
  Detail Goods ID=1001
</NavLink>
```

`Link` / `NavLink` 都会在客户端切换地址，而非让浏览器完整刷新文档；因此 React 的状态通常能保留，速度也更自然。

| 组件 | 用途 |
|---|---|
| `<Link to="...">` | 普通站内链接。例如 `DashboardLayout` 中的 `to="profile"`。 |
| `<NavLink to="...">` | 功能与 `Link` 相同，额外知道自己是否正匹配当前地址，适合导航菜单的「当前项高亮」。 |

当前写法给 `NavLink` 的 `className` 是固定字符串，因此激活状态不会有视觉变化。需要高亮时可传函数：

```tsx
<NavLink
  to="/about"
  className={({ isActive }) => (isActive ? 'text-red-500' : 'text-gray-500')}
>
  About
</NavLink>
```

### 3. 编程式导航：`useNavigate`

```tsx
const navigate = useNavigate()

navigate(-1)
navigate('/detail/1001', { state: { name: 'ABC', age: 12 } })
```

当跳转由事件、请求成功、权限判断等代码触发时，用 `useNavigate()` 得到的 `navigate` 函数。

- `navigate('/somewhere')`：跳到目标地址，默认会新增一条浏览器历史记录。
- `navigate(-1)`：相当于浏览器后退；`1` 则相当于前进。
- `navigate('/somewhere', { replace: true })`：用目标地址替换当前历史项；用户按后退不会回到被替换页面。
- `navigate('/somewhere', { state: data })`：携带路由 state，目标页由 `useLocation()` 读取。

`NavLink`/`Link` 适合「渲染一个可点击链接」，`navigate` 适合「在逻辑中决定何时跳转」；两者不要机械互换。

### 4. 三种传参方式：路径参数、查询参数、路由 state

#### 路径参数（path params）

```tsx
<Route path="/detail/:id" element={<Detail />} />
// URL: /detail/1001

const { id } = useParams() // { id: '1001' }
```

`:id` 是 URL 路径的一部分，适合资源标识，例如商品详情 `/detail/1001`。注意 `useParams()` 得到的是字符串（或 `undefined`），若业务需要数字，应显式校验和转换：`const goodsId = Number(id)`。

#### 查询参数（search params）

```tsx
// URL: /about?name=querySearch&age=18
const [searchParams, setSearchParams] = useSearchParams()
const name = searchParams.get('name')
```

查询参数位于 `?` 后，不改变 `/about` 这条路由的匹配结果，适合筛选、排序、分页、可选条件等可分享的页面状态。`get()` 返回 `string | null`，不要假定它一定存在。

更新查询参数必须放在事件处理函数或副作用中，例如：

```tsx
<button onClick={() => setSearchParams({ name: 'Vunbo', age: '18' })}>
  更新查询参数
</button>
```

#### 路由 state（location state）

```tsx
<NavLink to="/detail/1001" state={{ id: 123, name: 'test' }} />
const location = useLocation()
console.log(location.state)
```

路由 state 不显示在 URL 中，适合「从上一页临时带来的上下文」，例如列表页来源、动画信息、提交后的提示。它不能取代真实的资源 ID 或共享链接参数：用户直接访问 URL、复制 URL 给他人、或刷新后的表现都不应依赖它。`location.state` 的初始值可能是 `null`，实际项目读取时要判空。

简单选择原则：**资源 ID 用路径参数；筛选/分页等要可复制的状态用查询参数；仅本次跳转临时携带的数据用 `state`。**

### 5. 重定向：`Navigate` 与 `replace`

```tsx
<Route path="/" element={<Navigate to="/about" replace />} />
```

`<Navigate>` 是「渲染到这里就立刻导航」的声明式写法。这里访问 `/` 会进入 `/about`，且 `replace` 会将 `/` 从历史记录中替换掉，避免用户后退后又被立刻重定向一次。

`/dashboard` 的默认子页也使用了同样思路：

```tsx
<Route path="/dashboard" element={<DashboardLayout />}>
  <Route path="/dashboard" element={<Navigate to="profile" replace />} />
</Route>
```

在嵌套路由中，子路由更常见、也更清晰的写法是使用 `index`：

```tsx
<Route path="/dashboard" element={<DashboardLayout />}>
  <Route index element={<Navigate to="profile" replace />} />
  <Route path="profile" element={<Profile />} />
</Route>
```

其中 `index` 表示「父路径刚好匹配时的默认子路由」，即 `/dashboard`；`to="profile"` 是相对父路由的跳转，最终地址为 `/dashboard/profile`。

### 6. 嵌套路由与相对路径

```tsx
<Route path="/dashboard" element={<DashboardLayout />}>
  <Route path="profile" element={<Profile />} />
</Route>

// DashboardLayout 内
<Link to="profile">Profile</Link>
<Outlet />
```

父路由 `/dashboard` 匹配后，`DashboardLayout` 会始终渲染；继续匹配 `profile` 后，`Profile` 被放到父组件的 `<Outlet />` 内。子路由写 `path="profile"`，链接写 `to="profile"`，都是**相对父路由**，组合后就是 `/dashboard/profile`。这让模块迁移或修改父路径时更省事。

没有 `<Outlet />` 时，URL 虽然可能匹配子路由，但子页面没有位置可渲染，这是嵌套路由最常见的遗漏。

### 7. 404 兜底路由

```tsx
<Route path="*" element={<Home />} />
```

`*` 匹配未被前面路由匹配到的地址，通常用于 404 页面。当前 `Home` 返回的是 `404`，因此命名为 `NotFound` 会更贴合职责；若它是真正首页，则应另设 `/` 对应的首页路由。

### 8. 路由守卫（认证路由）的正确嵌套方式

`AuthRoute` 的设计方向是对的：有 token 时返回 `<Outlet />` 放行；没有 token 时用 `<Navigate>` 到 `/login`，并通过 `state.from` 记住原路径。

但当前路由表写的是：

```tsx
<Route element={<AuthRoute />} />
```

它没有子 `<Route>`，因此守卫没有包住任何页面，实际不会保护任何路由。应把需要登录的路由作为它的子路由：

```tsx
<Route element={<AuthRoute />}>
  <Route path="/dashboard" element={<DashboardLayout />}>
    <Route index element={<Navigate to="profile" replace />} />
    <Route path="profile" element={<Profile />} />
  </Route>
</Route>
```

之后还需要定义 `/login` 页面；登录成功后读取 `location.state?.from`，再 `navigate(from ?? '/', { replace: true })`，即可回到用户原本想访问的页面。

### 9. 两个常见坑

1. **Render 阶段改路由状态**：在组件函数体里直接 `setSearchParams(...)` / `navigate(...)` 会在 render 阶段触发更新，可能重复导航 / 重复渲染。应放到点击事件或 `useEffect` 中；render 保持纯粹。
2. **守卫没有子路由**：只写 `<Route element={<AuthRoute />} />` 却不嵌套受保护的子 `<Route>`，守卫等于没包住任何页面。

额外：路径参数（如 `/detail/1001` 的 `id`）与 `location.state.id` 语义不同，不要混用。资源 ID 以 URL 为准。

## `RTK` / `useSelector` / `useDispatch`：整体用法

**日期：** 2026-07-24
**相关文件：** store/

**疑问：** Redux Toolkit 在本项目里怎么串起来？`react-redux` 里 `useSelector`、`useDispatch` 分别干什么？和 RTK 包的分工是什么？

**结论：**

**分层（别混包名）**

| 包 | 职责 |
|----|------|
| `@reduxjs/toolkit` | `configureStore`、`createSlice`、内置 Immer、默认 middleware |
| `react-redux` | `<Provider store>` 挂 store；组件里 `useSelector` 读、`useDispatch` 写 |
| `redux` | 底层 store / reducer / action 模型（RTK 封装，一般少直接写） |

**本项目数据流**

1. **Slice**（`toolkit.ts`、`user.ts`）：`createSlice({ name, initialState, reducers })` → 导出 **action creators**（如 `increment`）和 **reducer**；reducer 里可「直接改」`state`，Immer 负责不可变更新。
2. **Store**（`index.ts`）：`configureStore({ reducer: { counter, user } })` → 根 state 形如 `{ counter, user }`；导出 `RootState`、`AppDispatch` 给 TS。
3. **入口**（`main.tsx`）：`<Provider store={store}>` 包住应用，子树才能用 hook。
4. **组件**（`10-sandbox.tsx`）：`useSelector` 取数 + `dispatch(actionCreator())` 改 state。

**两个 hook**

| Hook | 作用 | 类比 Pinia |
|------|------|------------|
| `useSelector(selector)` | 订阅 store，selector 返回值与上次 **!==** 时重渲染 | 读 store 里某字段，依赖变化才更新视图 |
| `useDispatch()` | 返回 `dispatch`，派发 slice 的 action（或 thunk） | 调 store 上的 action 方法 |

`useDispatch<AppDispatch>()`：让 TS 识别 RTK 的 action / `createAsyncThunk` 等，避免裸 hook 类型过窄。

**注意：** selector 不要每轮返回新对象（如 `(s) => ({ x: s.a })`），否则浅比较认为变了、会多余重渲染；只选需要的标量/稳定引用，或 `shallowEqual`。

**相关代码（自洽摘录）**

## `memo` / `useMemo` / `useCallback`：何时稳引用

**日期：** 2026-07-22

**疑问：** 用了 `memo` 是否 props 都要再包 `useMemo`？基础类型 / `useState` 对象 / 引用类型怎么区分？

**结论：**

`memo` ≈ Class `PureComponent`：对 props **浅比较**。`useMemo`/`useCallback` 不是标配，只负责「别每轮 render 换新引用」。

| 情况 | 要不要稳引用 |
|------|-------------|
| `string` / `number` / `boolean` / `null` | 不用 |
| `useState` / `useReducer` 吐出的值（已稳定） | 不用再包 |
| 上游已稳定的 `props.xxx`、模块顶层常量 | 不用 |
| 每轮新建的 `{}` / `[]` / `() => {}` / `.filter()` 结果当 props | 要：对象/数组用 `useMemo`，函数用 `useCallback` |

口诀：**不是「引用类型 = 必须 useMemo」，而是「会不会每轮换新引用」。** 会换且子组件靠 `memo` 跳过时才处理。

useState 存对象时：引用变不变取决于你怎么 set。不可变更新（{ ...prev, x }）才是新引用；原地改再 set 同一对象会 bail out，也会坑 memo。

`useMemo` ≈ Vue `computed` 的「缓存派生值」，但依赖靠手动数组，不是自动追踪。有 React Compiler 时，默认少手写这三件套；未开则按需（先 Profiler）。

```tsx
const Row = memo(function Row({ item, onSelect }: {
  item: Item
  onSelect: (id: string) => void
}) {
  return <button onClick={() => onSelect(item.id)}>{item.name}</button>
})

function List({ items }: { items: Item[] }) {
  const [q, setQ] = useState('')
  // ❌ 每轮新数组 / 新函数 → memo 子组件几乎总重渲染
  // <Row item={items[0]} onSelect={(id) => {}} />
  // <Row item={items.filter(...)[0]} />

  // ✅ 引用稳定时，父因 q 重渲染，Row 可跳过
  const visible = useMemo(
    () => items.filter((i) => i.name.includes(q)),
    [items, q],
  )
  const onSelect = useCallback((id: string) => {
    console.log(id)
  }, [])

  return visible.map((item) => (
    <Row key={item.id} item={item} onSelect={onSelect} />
  ))
}
```

## `render prop`：React 作用域插槽

**日期：** 2026-07-20
**相关文件：** 10-sandbox.tsx

**疑问：** Vue 作用域插槽由外部决定子组件如何展示，React 怎么实现？

**结论：**

作用域插槽 = **子组件持有数据，调用父组件传入的函数来渲染**（render prop / function as children）。

| Vue | React |
|-----|--------|
| `<template #item="{ row }">` | `renderItem={(row) => ...}` |
| 单个作用域默认插槽 | `children={(row) => ...}` |

```tsx
type Item = { id: number; name: string }

function List({
  items,
  renderItem,
}: {
  items: Item[]
  renderItem: (row: Item) => ReactNode
}) {
  return (
    <ul>
      {items.map((row) => (
        <li key={row.id}>{renderItem(row)}</li>
      ))}
    </ul>
  )
}

<List
  items={items}
  renderItem={(row) => <button type="button">{row.name}</button>}
/>
```

职责：子组件管数据 / 循环 / `key`；父组件管 `row` 的 UI。

和具名内容 props 的区别：`header={<...>}` 是父组件塞现成节点；render prop 是子组件先有数据再交给父函数画 —— 后者才对应 Vue **作用域**插槽。

## React 插槽 / Vue 具名插槽

**日期：** 2026-07-20
**相关文件：** 10-sandbox.tsx

**疑问：** `children` 塞多个兄弟节点不合理；React 有没有类似 Vue 具名插槽的写法？

**结论：**

React 没有运行时「插槽」概念。对应关系：

| Vue | React |
|-----|--------|
| 默认插槽 `<slot />` | `children` |
| 具名插槽 `#header` | `header` / `body` 等 `ReactNode` props |
| 作用域插槽 `#item="{ row }"` | render prop：`item={(row) => ...}` |

多块内容优先用具名 props，不要把多个区域全塞进 `children` 再拆：

```tsx
type Props = {
  header?: ReactNode
  body?: ReactNode
  footer?: ReactNode
}

function ShowComponent({ header, body, footer }: Props) {
  return (
    <>
      {header}
      {body}
      <hr />
      {footer}
    </>
  )
}

<ShowComponent
  header={<div>Hello</div>}
  body={<Component1 />}
  footer={<Component3 />}
/>
```

`children` 适合「只有一块主内容」的包装组件；若硬要用类型/运行时限制单个 child，可用 `ReactElement` + `Children.only`，或 `Children.toArray(children)[0]` 只渲染第一个（后者偏 workaround，不如具名 props 清晰）。

## 数组浅拷贝：改对象字段

**日期：** 2026-07-19
**相关文件：** 10-sandbox.tsx

**疑问：** 更新列表项时，`[...arr]` / 传 index 再 `newArr[i].count += 1`，和 `map` + `{ ...item }`，哪种合适？前者是否也算不可变更新？

**结论：**

`map` / `[...arr]` 都只保证**新数组**；数组里的对象仍是原引用。因此：

```ts
// ❌ 不能这样：外层像换了，里层其实在原地改旧对象
const next = [...cars];
next[index].count += 1;
setCars(next);
```

| 层级 | `[...arr]` + 改字段 | 结果 |
|------|---------------------|------|
| 父 `setState` | 数组是新引用 | **会** re-render（不是 set 失败） |
| `memo` / `PureComponent` 行组件 | 传下去的 `car` 仍是原对象 | `prev.car === next.car` → **跳过 render**，UI 不更新 |

无 `memo` 时父自己读 `count`，界面常「看起来正常」；一旦行组件 `memo(Row)({ car })`，改动的那一行就被浅比较挡掉——这才是不能靠 `[...arr]` 原地改字段的原因。

正确做法：**新数组 + 被改那一项也是新对象**。有稳定 `id` 时优先按 id；传 index 也可以，但要**换元素**而不是改字段。

```ts
// ✅ map：只换被改的那一项
setCars((prev) =>
  prev.map((car) =>
    car.id === id ? { ...car, count: car.count + 1 } : car
  )
);

// ✅ 按 index：先浅拷贝数组，再换该下标为新对象
const next = [...cars];
next[index] = { ...next[index], count: next[index].count + 1 };
setCars(next);
```

对照 Vue：`reactive` 可直接改字段；React `useState` 要整份 snapshot 换新引用，`memo` 只浅比 props。

## `Record<string, User>`

**日期：** 2026-07-17
**相关文件：** 05-effects-query.tsx

**疑问：** `const DB: Record<string, User>` 这个 TS 类型是什么意思？

**结论：**

`Record<K, V>` 表示「键为 `K`、值为 `V` 的对象」，`Record<string, User>` 等价于 `{ [key: string]: User }`。

| 场景 | 写法 |
|------|------|
| 任意 string key | `Record<string, User>` |
| 固定几个 key | `Record<'u1' \| 'u2' \| 'u3', User>` |
| Map 结构 | `Map<string, User>`（运行时是 Map） |

用 `DB[id]` 取值类型是 `User | undefined`（任意 string 都可能不存在），所以要做空值判断。

```ts
type User = { id: string; name: string }

const DB: Record<string, User> = {
  u1: { id: 'u1', name: 'Ada' },
  u2: { id: 'u2', name: 'Lin' },
}

function getUser(id: string): User | undefined {
  return DB[id] // id 任意 string → 可能没有
}
```

## `sort`：随机比较洗牌

**日期：** 2026-07-15
**相关文件：** 02-list-form.tsx

**疑问：** `setItems((prev) => [...prev].sort(() => Math.random() - 0.5))` 这个算法在干什么？

**结论：**

用 `Array.sort` 的比较函数做**简易洗牌**（demo 够用，非严格均匀随机）。

```ts
;[...prev] // 拷贝，不可变更新
  .sort(() => Math.random() - 0.5)
// compare 返回负/正 → 随机决定谁排前；每次比较都随机，顺序被打乱
```

目的：打乱列表顺序，方便观察 list `key`（尤其 index key）在重排时对不上的问题。

正式场景用 Fisher–Yates；`sort` + 随机比较不保证均匀分布。

## `useRef`：跨渲染可变盒子（非 UI 状态）

**日期：** 2026-07-12
**相关文件：** 01-mindset.tsx

**疑问：** `useRef` 在 React 里是不是主要用于数据存储？和 Vue `ref` 是不是一回事？

**结论：**

核心不是「通用数据仓库」，而是：**跨渲染保留一个可变值，改 `current` 不触发重渲染**。

| 需求                      | 用         |
| ------------------------- | ---------- |
| 变了要反映到 UI           | `useState` |
| 变了不需要 UI，只要记得住 | `useRef`   |

常见用途：挂 DOM、存 timer/AbortController、记上次值、渲染计数。

名字撞车：Vue `ref` ≈ React `useState`（响应式/驱动 UI）；React `useRef` ≈ 可变盒子 / 句柄。

```tsx
function Counter() {
  const [n, setN] = useState(0)
  const renderRef = useRef(0)
  renderRef.current += 1 // 改 current 不触发重渲染

  const inputRef = useRef<HTMLInputElement>(null)

  return (
    <>
      <p>renders: {renderRef.current}</p>
      <input ref={inputRef} />
      <button onClick={() => inputRef.current?.focus()}>focus</button>
      <button onClick={() => setN(n + 1)}>{n}</button>
    </>
  )
}
```

## `ChapterId` 类型

**日期：** 2026-07-12
**相关文件：** App.tsx

**疑问：** `(typeof chapters)[number]['id']` 里，`[number]` 和取 `id` 是什么意思？

**结论：**

```ts
const chapters = [
  { id: '01', label: '...', Comp: Chapter01Counter },
  { id: '02', label: '...', Comp: Chapter02ListForm },
  // ...
] as const

type ChapterId = (typeof chapters)[number]['id']
// 等价于 '01' | '02' | '03'
```

拆开读（类型层，不是运行时取值）：

| 片段              | 含义                                              |
| ----------------- | ------------------------------------------------- |
| `typeof chapters` | 取 `chapters` 的类型                              |
| `[number]`        | 用任意数字下标取元素 → **所有元素类型组成的联合** |
| `['id']`          | 再取出联合里每一项的 `id` 字段类型                |

要点：

- `[number]` ≈「任意一项」：把元组/数组里各元素类型并成联合；不是只拿某一项。
- `['id']` 是 Indexed Access Types，语法像对象取值，作用在联合上会对每一项分别取 `id`。
- 需要 `as const`：否则 `id` 会宽成 `string`，推不出 `'01' | '02' | '03'`。

对比：

```ts
;(typeof chapters)[0]
  ['id'] // 只拿第一项 → '01'
  (typeof chapters)[number]['id'] // 任意一项   → '01' | '02' | '03'
```
